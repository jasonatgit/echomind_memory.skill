## 一、问题：只会"总结"的反思

### 1.1 今天的反思做了什么——以及为什么不够

EchoMind 的反思引擎读取情景记录（逐轮发生的事），蒸馏出长期知识。当一段交互表现不佳时，它产出类似「用户偏好简洁回复」的洞察——这是一份**总结**。总结并非无用，但它回答的不是问题真正重要的那一面。

真正重要的问题是：**记忆系统的哪一部分该变？**

看一个具体失败。一次智能体会话以用户不满结束。在其内部，四种病恰好有一种存在：

| 病症 | 组件 | 实际发生了什么 | 正确的修复 |
|---|---|---|---|
| **知识缺失** | E（经验） | 这条事实从未被存下——没有卡、没有条目 | 写入知识 |
| **知识从未被调用** | ρ（调用策略） | 它存在，但检索键/时机错过了它 | 修复调用时机或检索键 |
| **任务状态错误** | W（工作状态） | 追踪器记录了从未发生的完成 | 修复状态或其接地 |
| **纪律被突破** | C（检查器） | 无证据声称进展 | 收紧完成谓词 |

四种病产生**同一个可观测结果**：坏结局。四种病需要**不同的修复**。总结把它们塌缩成一个「这次很糟」的信号，把修复留给猜测——而猜错意味着下一次会话重演同样的失败，同时记忆系统还在累积无用的条目。

### 1.2 实证：定位准确率的测量

来自 NUS、斯坦福、牛津、普林斯顿的论文《Recursive Experiential–Working Memory Evolution for Long-Horizon Agent Harnesses》（Recuris，arXiv:2608.24876）给这种塌缩标上了数字。他们的系统记录**结构化执行轨迹**，把每个动作与"触发技能检索的状态、判定状态变更是否被接受的证据"关联起来：

```
Γ = ( x, { w_t, E_t, a_t, o_t, w̃_{t+1}, c_t, w_{t+1} }_{t=1..L}, y )
```

从左到右读这个元组：

- `x` — 任务指令
- `w_t` — 第 `t` 步**经验证的工作状态**（做完了什么、还差什么）
- `E_t` — 第 `t` 步**调用的经验/技能**
- `a_t`、`o_t` — 动作与环境观测
- `w̃_{t+1}` — **提议**的下一状态（尚未验证）
- `c_t` — **检查器判定**（哪些提议的状态转移被接受）
- `w_{t+1}` — **已提交**的下一状态
- `y` — 最终结果

轨迹的价值在试图把失败定位到组件时显现：

| 诊断者可用的证据 | 定位准确率 |
|---|---|
| 仅最终任务结果 `y` | **13.0%** |
| 原始轨迹 `{(a_t, o_t)}` | 37.0% |
| **结构化 trace `Γ`** | **64.8%** |

从 13.0% 到 64.8% 不是渐进式改进——它是"能对失败采取行动的系统"与"只能报告失败的系统"之间的区别。**没有 trace，系统大约五分之四的时候说不出该修哪个组件。** 为什么？因为四种病里有两种是**非事件**：「本该被调用却没有调用的知识」在原始转录里不留痕迹——检索本应出现的位置上，什么都没有。只有一份记录了*调用时刻存在什么状态*的结构化档案，才能让"缺席"变得可见。

### 1.3 为什么"记忆状态"比"记忆内容"更重要

论文的消融对价值所在毫不含糊。逐个加入记忆组件、测量任务成功率：

```
Δ(仅 E)   = +2.0 分     # 只加技能卡，别的都不加
Δ(W + ρ)  = +23.9 分    # 加经验证的状态与调用策略
```

决定**何时调用**的机器，比被调用的内容重要一个数量级。内容是入场券，**接地的状态**才是产品。这是 EchoMind 从 Recuris 学到的最重要一课，因为它重新定义了一个记忆系统该优化什么：不是"存更多"，而是"把当下处境了解得足够清楚，从而用得上你存的东西"。

EchoMind 是记忆引擎、不是执行 harness：它不驱动智能体，因此无法像 Recuris 那样从工具回执里造出一个工作状态。它能做的是让检索**可观测**（trace）、让失败**可归因**（反思字段）——这两个正是未来闭合状态回路的前提条件。

## 二、Recuris 的不同之处

Recuris 演化的是冻结智能体的 **Skill Memory** `M = (E, W, ρ, C)`，而不是它的权重或 prompt。智能体本身不动；变的只是外部的记忆控制层：

- **E** — 经验记忆：从失败蒸馏出的技能卡（与 EchoMind 的 `knowledge_memory` / `experience_memory` 同构）
- **W** — 工作记忆：经证据验证的任务状态账本，条目只在真实工具回执接地后才推进到 `DONE`
- **ρ** — 调用策略：在哪些执行事件、依据当前工作状态，交付哪些卡片
- **C** — 检查器：声称进展前必须成立的完成谓词

两个嵌套闭环让它"递归"。**任务内**，工作状态引导技能调用；执行后，经验证的反馈更新状态。**跨任务**，一个固定的 Meta-Agent 读取失败运行的结构化轨迹，把每个失败归因到恰好一个组件，只修补那个组件，而**验证门**只在配对 held-out 证据上决定是否准入。门是纯算术——没有模型为自己的补丁投票。

论文的三个发现塑造了我们的吸收选择：

1. **状态接地调用胜过内容检索。** 从初始指令或完整聊天历史检索会随历史增长而退化；从紧凑、经验证的状态检索不会。
2. **结构化证据使定向修复成为可能。** 因为轨迹记录了状态、调用的技能、动作与检查，失败可以被定位到组件——而组件级补丁远比整体重写安全。
3. **弱证据必须弃权，而非拒绝。** 他们的门只在配对 bootstrap 置信区间排除零**且**回归数在 cap 之内时准入；当证据无法分辨问题时，门弃权——因为统计上功效不足的"否"不是一个真正的否。

## 三、定位问题：Harness 与记忆引擎

Recuris 是一个 **agent harness**——它驱动执行、看得到工具回执、能重放环境。EchoMind 是一个**记忆引擎**——它不驱动智能体，只负责存储、排序、返回记忆。这个差异对"什么能迁移"是决定性的：

| Recuris 机制 | 是否适用于 EchoMind | 理由 |
|---|---|---|
| 结构化执行 trace | ✅ 是 | 检索本就算出了原始素材，只是没被记录下来 |
| 组件级归因反思 | ✅ 是 | EchoMind 的 6 个子 Agent 是天然、稳定的 patch 空间 |
| Fingerprint（"先读机制再读分数"） | ✅ 是 | `hit_history` 已记录机制，只是没被强制 |
| 配对 bootstrap 验证门 | ✅ 是 | 基于 `hit_history` / 条目可观测性重建，而非环境重放 |
| 经验证工作状态（意图账本） | ⚠️ 部分 | 记忆引擎没有工具回执通道；状态只能和调用方给的证据一样接地 |
| 任务状态条件化调用 | ⚠️ 部分 | 没有**实时**执行状态可供条件化；记录型任务清单是更弱的信号 |
| Status board / truth guard / 领域 oracle | ❌ 否 | 它们拦截智能体的草稿消息、验证工具回执；EchoMind 没有草稿可拦截 |
| 每域手写 matcher | ❌ 否 | 没有可绑定匹配键的环境重放 |

我们用一条规则给每个候选排序：**解决已被证实的 EchoMind 痛点、成本相称、前置条件就绪。** 论文自身的消融指导了排序——实验中显示冗余的组件被降权：

- **E 单独贡献很小**（+2.0）：没有状态接地调用的技能内容推不动指针，因此我们优先做 trace 与归因，而不是"多存卡"。
- **truth guard 的事后审计是惰性的**：它拒绝了 172 次不支持的完成声明却零可测效果，因为等到审计运行时，动作早已改变了环境。一个只能在事后抱怨的守卫，不值得移植。

## 四、v1.2.19 落地了什么：Top-4

### 4.1 结构化检索 trace（迁移 v12）

**它解决的问题。** 今天，当一次记忆查找没返回有用东西时，没有一份持久记录说明*问了什么、有哪些候选、各自排在哪里*。调试记忆行为意味着重读对话、然后猜。Recuris 的 13% 正是这种盲区的代价。

**建了什么。** 每次 `retrieve_for_task` 现在把一条 `trace-v1` 记录持久化到会话的 context 行：

```json
{
  "schema": "trace-v1",
  "query": "python refactor",
  "retrieved": [
    {"id": "k:482...", "source": "knowledge", "importance": 0.78},
    {"id": "exp:91...", "source": "experience", "importance": 0.61},
    {"id": "ctx:sessA", "source": "context", "importance": 0.40}
  ],
  "retrieved_counts_by_source": {"knowledge": 3, "experience": 2, "context": 1},
  "top_n": 3,
  "captured_at": "2026-09-25T08:00:00+00:00"
}
```

组装过程**复用评分本就在构建的聚合检索字典**——没有第二次查询、没有额外扫描、没有新模型调用。配套的 `save_context_trace` 只更新 trace 列、不重写（可能很大的）消息载荷。旧行保持 `trace='{}'`，行为与之前完全一致。

**为什么 trace 里的数字可信。** `importance` 不是事后计算的摘要——它就是排序实际使用的分数，由统一评分契约产出：

```
freshness(record) = 2^( -Δ天数 / half_life )          # 艾宾浩斯衰减，half_life = 69 天
base  = Σ(值_i × 权重_i) / Σ(权重_i)                  # 各源归一化基分 ∈ [0,1]
score = base × freshness × soft(origin)               # 单一 recency 杠杆 + 跨源惩罚
```

具体地，knowledge 条目的基分在 RL 权重下组合内容相关性与可信度；experience 条目额外折入对数缩放的频率项：

```
knowledge:  base = (relevance·w_rel + trust·w_trust) / (w_rel + w_trust)
experience: freq_n = min(1, log1p(freq)/log1p(20))
            base = (rel·w_rel + freq_n·w_freq + trust·w_trust) / (w_rel + w_freq + w_trust)
```

因为每个因子要么存储在记录上、要么读自当前权重向量，**任何一条 trace 都能在日后从数据库精确重导**。trace 是证据，不是转述。

**深度说明——为什么用独立列。** trace 本可以塞进 `messages`，但那样会（a）膨胀对话载荷、（b）让证据与消息重写耦合、（c）使"给我看 top 结果 importance < 0.3 的检索"这类查询变得别扭。独立列让证据保持一等公民身份且可查询，同时不触碰转录语义。

### 4.2 组件归因反思

**它解决的问题。** 一份说"这次很糟"的反思给不出修复目标。Recuris 定位到四个组件之一；EchoMind 的对应物是它的六种记忆类型之一，外加一个显式的"无法归因"态。

**建了什么。** `ReflectionOutput` 新增两个字段：

- **`primary_owner`** — 本次反思把发现归因到哪个记忆组件：`knowledge | experience | task | context | user | research | none`
- **`failure_type`** — `knowledge_gap`（知识缺失）或 `invocation_miss`（知识存在但从未被及时检索）

两者默认 `""`（未归因），因此旧版 LLM 输出与第三方调用方完全不受影响。中英反思 prompt 现在要求归因，并带一条显式**弃权规则**：*不要把模糊性强行变成归因——不确定时用 "none"。* 这条规则直接借自 Recuris 的诊断协议，在那里"什么都不提议"（`fixes: []`）是一等公民，而非失败。

**修复决策的形式化形状。** 归因是组件上定位后验的 argmax：

```
归因(Γ) = argmax_{c ∈ {E,W,ρ,C}}  P( 组件 c 需要修复 | Γ )
```

我们不假装用一个模型去估计这个后验——那恰恰是弃权规则所禁止的过度自信猜测。反思产出的是一个**离散**归因外加显式弃权态，且只有被归因的发现才有资格进入分组件动作。EchoMind 组件到记忆类型的映射是直接的：

| 归因 | EchoMind 目标 | 典型修复 |
|---|---|---|
| `knowledge` | `knowledge_memory` | 新增/改写可复用条目 |
| `experience` | `experience_memory` | 新增成功/失败经验 |
| `task` | `task_memory` | 更正被追踪的任务状态 |
| `context` | `context_memory` | 重新关联会话上下文 |
| `user` | `user_memory` | 新增偏好/习惯 |
| `research` | `research_papers/notes` | 新增参考 |

**深度说明——它暴露的双引擎 bug。** EchoMind 有两个反思引擎：编译型 native 引擎与 Python fallback。fallback 在内部归一化归因字段，但 **native 引擎直接返回 `ReflectionOutput` 对象，完全绕过了 fallback 的归一化**。于是畸形的 `primary_owner: "bogus"` 在 native 路径上一路通行、本会被原样持久化。修复把归一化移到 `ReflectiveAgent._normalize_attribution`——两个引擎都必须经过的唯一单点：

```
normalize(x) = x.lower().strip()   若 x ∈ 合法集合
             = ""                  否则              # 未知 → 未归因
```

这正是"吸收不是复制粘贴"的一个好例子：同一条语义要求，在 EchoMind 的架构里必须在与 Recuris 不同的层上强制。

### 4.3 Fingerprint 门：零观测 ≠ 信号

**它解决的问题。** EchoMind 的 RL 优化器根据用户反馈调整检索权重，并周期性检查学习是否真的有效。检查把近期命中率与基线对比：

```
success  = (1/n) Σ hits_i
baseline = (1/m) Σ baseline_j
se       = sqrt( success(1 − success) / n )
improved = success > baseline + 2·se          # 约 95% 单侧
```

盲点在于：`verify_improvement` 把窗口内的每一条反馈都当作证据，**包括那些针对从未被检索过的条目的反馈**。`access_count = 0` 的条目没有观测——它的"有效性"没有定义，在上面测到的任何差异都是噪声。作用于噪声比什么都不做更糟：一段安静期可能无缘无故触发保守阶梯（"不显著 → 学习率减半"）。

**建了什么。** Recuris 的 fingerprint 原则——*先读机制再读分数*；他们的 scorecard 拒绝在机制计数器之前打印分数——现在被强制到门上：

```
observed = #{ 该用户知识中 access_count > 0 的条目 }
若 observed == 0:
    返回 insufficient        # 无信号——不运行保守阶梯
```

两处具体改动：

- `verify_improvement(hits, baseline, observed_count=...)`——**零观测条目**的窗口报 `insufficient`（而非 `not_significant`），保守阶梯因此永远不会被噪声触发。完全省略 `observed_count` 时，行为与之前完全一致（向后兼容）。
- `record_feedback` 现在在 `save_hit` 上记录 `task_type`（此前恒 `''`），命中统计不再只按用户维度——你能看到**哪类任务**学得好。

**深度说明——为什么用 `access_count`。** `hit_history` 是事件级的：每次反馈一行。要知道某个*条目*是否曾被观测，需要一个条目级计数器，而 `knowledge_memory.access_count` 正是它——每次检索返回该条目时递增。用它让门保持零依赖（没有新表）且可从存储数据复现。

### 4.4 配对 bootstrap 门（灰度）

**它解决的问题。** 记忆系统通过改写知识来演化。改得不谨慎，一次改写就可能凭一次幸运或不幸的读数静默劣化知识库。Recuris 的答案是"算术准入"：*模型提议，算术处置。*

**建了什么。** `core/learning/paired_gate.py` 实现同样的语义，经 `reflection.gate_enabled` 接入反思合并——**灰度默认关**。给定同一组 held-out item 上的配对分数：

```
diffs_i = cand_i − base_i                       （每个 item 一个值）
net     = mean(diffs)
floor   = max(material, 1e-9)
n_up    = #{ diffs_i >  floor }
n_dn    = #{ diffs_i < −floor }

# bootstrap 重采样的是 ITEM，不是样本
boots   = sorted{ mean( diffs[randrange(n)] for _ in range(n) ) } × 3000 次
lo, hi  = boots[α/2·B], boots[(1−α/2)·B − 1]

accept  = (lo > 0) and (n_dn ≤ reg_cap)
```

两个细节是承重的，且都容易做错：

1. **以 item 为单位 bootstrap，而非单样本。** 同一 item 内的试验是相关的；重采样它们会产出比证据支持的窄得多的区间——也就是凭空制造显著性。我们重采样整个 item（簇），与 Recuris 的 `held_out_paired_gate` 完全一致。
2. **"不显著"是弃权——不是拒绝。** Recuris 的 Case 1 记录了两个被低功效门拒绝的补丁，事后在 held-out 任务上测得 **+11.92**。把"分辨不了"当作"否"的门会摧毁真实的改进。`material` 下限进一步阻止 0.97 vs 0.95 的噪声被登记为回归——否则回归 cap 会被纯抖动触发。

**深度说明——为什么是灰度。** 准入门会改变行为，而一个能拒绝更新的变化不应默认开启。门默认关；启用是操作者的刻意选择，且它的语义只在一个方向上保守——它可以拒绝一个好的更新，但不能准入一个显著有害的更新。

## 五、这些吸收给用户带来什么收益

价值不是抽象的。每一项吸收都对应着你能观察到或据此行动的东西：

| 吸收项 | 你得到什么 | 为什么对你有价值 |
|---|---|---|
| 结构化 trace | **可复现的检索审计**——"为什么没记住 X？"从存储行回答，而非回忆 | 你能像调试其他系统一样调试记忆，而不是当黑盒 |
| 结构化 trace | **归因成为可能**——反思层可把坏结局关联到具体检索事件（64.8% vs 13.0%） | 失败变得可行动，而不只是被报告 |
| 结构化 trace | **精确重导**——每个 `importance` 都能从记录 + 当前权重复现 | 你能证明某条记忆为何排在那个位置 |
| 组件归因 | **定向修复而非散弹式改动**——`invocation_miss`（ρ）靠改检索时机（价值 +23.9），而不是写入更多知识（+2.0） | 知识库更少无效改动；更少低价值条目 |
| 组件归因 | **诚实的不确定性**——系统说"无法归因"而不是编造原因；弃权是一等公民 | 更少"自信但错误"的诊断；你更信任得到的归因 |
| 组件归因 | **可查询的历史**——owner/failure_type 写入反思 `meta` JSON | "这个月有多少条 `invocation_miss` 反思"是一个查询，而不是考古 |
| Fingerprint 门 | **噪声不再触发误罚**——安静期不再仅凭噪声触发"不显著 → 学习率减半" | 你的检索权重不再凭空虚漂 |
| Fingerprint 门 | **可信的学习历史**——命中记录带上了 `task_type` | 你能看到**哪类任务**学得好 |
| 配对门 | **记忆只在配对上改变**——准入需 `lo > 0` 且 `n_dn ≤ reg_cap`；弱证据弃权并保留当前知识 | 你的知识库不会因一次抛硬币式读数而静默退化 |
| 配对门 | **下行有界**——每次被应用的改写都可证明不是显著回归 | 可放心启用；且默认关，未启用前一切不变 |

**运行成本。** 以上在未启用时零成本。trace 搭载在检索本就要算的数据上；门默认关；归因字段默认 `""`，任何不读它的调用方都会忽略。这次升级加了一列和两个可选字段，不是一个新子系统。

## 七、结论

Recuris 证明了递归自我改进可以活在冻结智能体的**记忆层**里——并且反思引擎的职责不是总结失败，而是**定位**到可修复的组件。证据是量化的：定位准确率 13.0% vs 64.8%，以及哪个组件最关键差二十倍（+2.0 vs +23.9）。

EchoMind v1.2.19 取出了其中适配记忆引擎的四件机器：

1. 让定位成为可能的 **trace**，
2. 让修复精准的**归因**，
3. 把噪声挡在学习之外的 **fingerprint**，
4. 以及让演化被配对证据约束的**门**。

它们一起把反思从"总结生成器"变成"修复引擎"——并且在未启用时对用户零成本。
